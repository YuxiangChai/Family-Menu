# 自建 SQLite 数据库

启动服务时自动创建表和索引，无需数据库账号，也无需另外安装 MySQL。默认文件为 `server/data/menu.sqlite`；可用服务端 `MENU_DATA_DIR` 修改目录。

## 各表用途

| 表 | 内容 |
| --- | --- |
| `family_members` | 家庭成员：唯一 OpenID、昵称、固定管理员权限（role）、历史兼容字段 is_chef（不再生效）、启用状态 |
| `family_settings` | 家庭公共配置：邀请码的盐及 scrypt 校验值；另有照片签名密钥 |
| `categories` | 九个默认分类；保留已有菜和分类归属，不会创建示例菜 |
| `dishes` | 菜品信息；仅菜名必填 |
| `orders` | 已提交订单的最终结果及菜品/食材快照；提交者 + 提交标识联合唯一，不再新增份数或版本号 |
| `menu_change_receipts` | 当前菜单的增删去重键，仅菜单标识、操作人、请求键，不保存历史菜单内容 |
| `menu_submission_receipts` | 当前菜单标识到提交订单的映射，确保多人重复提交只保存一次 |
| `sessions` | 微信登录会话的 token 哈希、OpenID、到期时间（7 天） |
| `rate_limits` | 登录、接口和邀请码尝试频率计数 |
| `notifications` | 历史站内消息，仅保留旧数据，不再新增 |
| `notification_preferences` | 历史订阅配置，仅保留旧数据，不再使用 |
| `notification_outbox` | 历史发送记录，仅保留旧数据，不再执行队列 |

业务表的 `data` 列保存完整 JSON；用于查找、唯一性和约束的字段同时保存在独立列。服务内事务保证订单写入原子性。时间按 ISO 时间戳保存，订单日期按北京时间计算。

## 成员与设置的区别

`family_members` 一人一条，`role=admin` 表示唯一管理员，否则为 `member`；所有人都有用户身份。旧 `isChef` 字段不再产生任何权限。管理员在“我的 → 家庭成员管理”查看和修改称呼、启用状态；名单不返回 OpenID。也可使用 `npm run members` 查看脱敏名单。管理员权限不能通过 API 转让或新增。

`family_settings` 保存家庭级配置及共享当前菜单。固定 `family` 记录保存邀请码校验值，不保存邀请码明文；`_media-key` 记录保存图片签名密钥；`_current-menu` 只有一条，保存全家正在点菜或修改的菜单，提交或管理员结束后移除。**加入家庭会增加一条成员记录，不会增加一份家庭设置**。换邀请码不移除已经加入的成员。

## 菜品可选字段

唯一必须填写的是非空 `name`。其他用户填写字段允许空值：

- `categoryId`、`description`、`imageFileId`：空字符串。
- `cookingTime`：未填写为 `null`，不是强制填 0；旧 `defaultServings` 仅作数据兼容，不再在界面填写或用于计算。
- `ingredients`、`steps`：允许空数组；空白食材行和空白步骤会忽略。
- 有名称的食材可以不填用量、单位和备注，不会擅自填成 0。
- 若填了数字，则仍校验范围。食材仅合并参考用量，不根据份数或就餐人数自动放大。

菜品没有分类时在菜单显示“未分类”；上架状态和创建/更新时间由系统维护。没有食材的菜也可以下单，食材汇总为空。

## 权限、照片与备份

前端只调用 HTTP API，不直接打开 SQLite。服务向微信换取真实身份，每次请求再查 `family_members` 检查权限。所有已启用成员都能查看全家历史、今日订单和订单详情，包括加入前的订单，并共同操作唯一当前菜单。修改订单占用同一个当前菜单，不能同时另开一份。增删通过短事务锁合并，不再按 revision 拒绝并发修改。提交时保持原订单 ID、下单人和创建时间不变。菜品维护、图片上传、邀请码、成员管理和丢弃全家未提交菜单仍只允许管理员。未加入或停用的账号不能查看家庭数据。

启动时自动事务迁移到 schema version 4，保留成员 ID、OpenID、昵称、启用状态和其他元数据；旧成员默认没有厨师权限，管理员不变。唯一索引禁止第二个管理员。若旧库存在多个管理员，启动明确报错，不自动选择或删除成员。升级前应运行 `npm run backup`。

菜单增删和提交使用 `BEGIN IMMEDIATE` 事务锁，锁只持续一次写入，不锁住用户编辑过程。同一道菜最多一条；操作去重凭证避免网络重试复活已删除的菜，提交凭证保证同一菜单只生成一个订单。新菜单使用新标识，迟到请求拒绝操作下一餐。只保留最终已提交结果，不保存历史版本。旧订单份数和 revision 读时忽略、不批量重写；该订单被修改提交后去掉这些字段。为避免破坏旧 SQL 约束，新订单内部 status 列使用 completed 作为兼容值，不表示已经做饭，API 不再返回此字段。旧订单状态不重写。停用订阅消息，不再写入或发送通知。数据库无需保存 AppSecret 或 access_token。分类升级只在 `_categories-v2` 标记不存在时执行，旧默认分类改名并补充新分类，不移动或删掉菜品，不覆盖之后自行改名的分类。

照片文件位于数据目录下的 `uploads/`，数据库保存稳定的内部引用；返回前端时生成限时签名链接，并再次检查会话及成员状态。服务器不提供数据库、`.env` 或任意文件目录下载接口。

数据库包含真实 OpenID 和家庭数据，应保持在服务器受控目录中，不提交到 GitHub。使用根目录的 `npm run backup` 同时备份数据库和照片。部署、成员管理、恢复方法见 [主 README](../README.md)。旧集合说明见 [历史记录](cloudbase-legacy.md)。
